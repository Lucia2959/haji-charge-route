# 확장 기획 — 성수기 충전 혼잡 대응

> 여행·레저 도메인 관점의 차기 개발 프롬프트.
> 작성 2026-08-04 / 기준 커밋 `158539a`

---

## 1. 왜 이 문서인가

연휴·주말 성수기에 관광지 방향 도로에서 장시간 지체가 발생하고, 동시에 고속도로
휴게소 충전소에 수요가 몰린다. 전기차 운전자는 두 가지를 동시에 겪는다.

1. **정체로 예상보다 배터리가 빨리 닳는다** ← 이미 해결됨
2. **도착한 충전소가 만차라 30~60분을 더 기다린다** ← **미해결**

(2)가 (1)보다 치명적이다. 계획 시점에 "이 휴게소는 그 시각에 붐빈다"를 모르면
총 소요시간 예측이 통째로 빗나가고, 최악의 경우 다음 충전소까지 못 가는
**방전 위험**으로 이어진다.

## 2. 현재 앱과의 관계 — 무엇이 이미 있고 무엇이 없나

| 목표 | 현재 상태 | 근거 |
|---|---|---|
| 출발지부터 충전계획 수립 | ✅ | `charging.plan_charging_dp` — 충전커브 기반 시간최적화 |
| 방전 리스크 감소 | ✅ | 안전마진 절대하한 25km(`_MIN_BUFFER_KM`), 목적지 최소잔량 15%(`_DEST_MIN_SOC`), 선충전 권장, `feasible` 판정 |
| 공공/개방 충전소 현황·위치 | ✅ | 공공데이터포털 `getChargerInfo` + 개방여부 5분류(`_access_class`) |
| 정체로 인한 추가 소모 | ✅ | 카카오 `traffic_state` → `congestion_extra_kwh`. 저속에서 시간기반 보조부하(`_AUX_BASE_KW`)가 지배적 |
| 외부환경 보정 | ✅ | 온도(Open-Meteo)·속도·도로유형·회생 |
| **성수기 수요 쏠림 대응** | ❌ | — |
| **충전소 대기열·혼잡 예측** | ❌ | 순간 상태(`stat`)만 조회. 이력 없음 |
| **대도시 충전소 탐색 지도** | ❌ | 경로 기반 조회만 존재 |

**결론: 신규 개발이 아니라 확장이다.** 목표의 상당 부분은 이미 동작한다.

## 3. 시작 전에 반드시 인지할 제약

### 3.1 공공 API는 이력을 주지 않는다 → DB가 필요해진다

`getChargerInfo`는 **현재 상태만** 반환한다. 혼잡 예측을 하려면 직접 폴링해
시계열을 쌓아야 한다.

현재 앱은 **DB가 없다** — 인메모리 캐시(카탈로그 24h / 상태 20s)뿐이다.
따라서 이 확장의 가장 큰 변화는 기능이 아니라 **영속 저장소 도입**이다.
이는 "단일 인스턴스 + 단일 워커" 제약([03 아키텍처 2.3](03-시스템아키텍처.md))의
재검토로 이어진다.

### 3.2 일일 쿼터 때문에 전수 폴링이 불가능하다

계산 1회가 이미 시군구 20~24회를 부른다. 전국 충전소를 주기적으로 폴링하면
쿼터가 즉시 소진되고 **본 기능(경로 계획)이 먼저 죽는다.**
수집 대상을 좁히는 것이 설계의 출발점이다.

### 3.3 콜드스타트 — 데이터가 쌓이기 전엔 예측할 수 없다

의미 있는 (요일 × 시간대) 통계가 나오려면 최소 몇 주가 필요하다.
그 전에 추측값을 내면 **근거 없는 대기시간 예측이 방전 위험으로 직결된다.**

### 3.4 순서가 강제된다

**F1(수집기)을 먼저 배포해 데이터를 쌓기 시작하고, F2~F4는 몇 주 뒤에 붙인다.**
나머지 기능이 전부 F1의 데이터에 의존하기 때문이다.

## 배경 / 해결할 문제

연휴·주말 성수기에 강원권 등 관광지 방향 도로에서 장시간 지체가 발생하고,
동시에 고속도로 휴게소 충전소에 수요가 몰린다. 전기차 운전자는 두 가지를
동시에 겪는다.
  (1) 정체로 예상보다 배터리가 빨리 닳는다  ← 기존 앱이 이미 모델링함
  (2) 도착한 충전소가 이미 만차라 30~60분을 더 기다린다  ← 미해결

(2)가 (1)보다 치명적이다. 계획 시점에 "이 휴게소는 그 시각에 붐빈다"를 모르면
총 소요시간 예측이 통째로 빗나가고, 최악의 경우 다음 충전소까지 못 가는
방전 위험으로 이어진다.

## 기존 자산 (반드시 재사용, 재작성 금지)

- backend/app/services/charging.py — 소비모델·유효거리·충전커브 DP.
  외부 의존이 없는 순수 모듈이다. 이 성질을 깨지 말 것.
- backend/app/services/ev_stations.py — 공공 EV API 클라이언트, 카탈로그
  24h 캐시, 상태 20s 캐시, 개방여부 분류(_access_class).
- backend/app/services/kakao.py — 경로·실시간 교통(traffic_state)·행정동 코드.
- 문서 docs/01~05를 먼저 읽고 시작할 것. 특히 04-운영이슈의
  "절대 건드리면 안 되는 설정"을 위반하지 말 것.

## 새로 만들 것

### F1. 충전소 점유 이력 수집기
- 대상을 좁힌다: 고속도로 휴게소 + 주요 IC 인근 급속 충전소만.
  전수 폴링은 공공 API 일일 쿼터로 불가능하다.
- 수집 주기와 대상 개수를 쿼터 예산에서 역산해 정하고, 그 계산 근거를
  코드 주석에 남길 것.
- 저장: (충전소ID, 관측시각, 전체 충전기수, 사용중 수) 시계열.
- 앱 요청 처리와 분리된 워커로 돌린다. 사용자 요청 경로에 넣지 말 것.

### F2. 혼잡도 예측
- 입력: 충전소ID, 도착 예정 시각(요일·시간대·공휴일/연휴 여부 포함).
- 출력: 예상 점유율, 예상 대기시간(분), 신뢰도.
- 방식: 초기엔 (요일유형 x 시간대) 분위수 통계로 충분하다.
  ML 프레임워크를 도입하지 말 것. 통계로 부족함이 측정되면 그때 논의.
- 콜드스타트 필수: 관측치가 임계 미만이면 예측하지 않고
  "데이터 부족"을 명시적으로 반환한다. 추측값을 내지 말 것.

### F3. 계획에 대기시간 반영
- 현재 DP의 정지 오버헤드는 _STOP_OVERHEAD_MIN=12분 고정이다.
  이를 (고정 오버헤드 + 예측 대기시간)으로 바꾼다.
- 데이터 부족 시 기존 고정값으로 폴백한다.
- 결과 화면에 "이 충전소는 도착 예정 시각에 혼잡 예상(대기 25분)"과
  "한 정거장 앞 충전소로 바꾸면 총 40분 단축" 같은 대안을 함께 제시한다.

### F4. 출발 시각 추천
- 같은 경로를 여러 출발 시각으로 시뮬레이션해 총 소요시간을 비교한다.
- 출력 예: "2시간 일찍 출발하면 총 소요 1시간 30분 단축(정체 -50분,
  충전대기 -40분)". 근거를 분해해 보여줄 것.

### F5. 지역 충전소 탐색 지도
- 현재는 경로 기반 조회만 가능하다. 경로와 무관하게 시/군/구 단위로
  충전소 현황을 탐색하는 화면을 추가한다.
- 필터: 급속/완속, 외부인 이용가능 여부, 최소 출력(kW), 현재 사용가능.
- 마커가 수천 개가 되므로 클러스터링이 필요하다.

## 아키텍처 요구사항

- DB를 도입한다. 현재 앱은 DB가 없고 인메모리 캐시만 쓴다.
  시계열 저장·집계에 적합한 최소 구성을 고르고 이유를 설명할 것.
  (SQLite로 시작해도 되는지, Postgres가 필요한지를 데이터 증가율로 판단)
- 수집 워커와 API 서버의 배포 형태를 정할 것. 현재는
  "단일 인스턴스 + 단일 워커"가 인메모리 캐시 때문에 강제되어 있다.
  DB 도입이 이 제약을 풀어주는지, 아니면 유지해야 하는지 판단하고 명시할 것.
- 외부 API 동시 호출 상한 _FETCH_CONCURRENCY=4를 올리지 말 것.
  실측상 8이면 공공 API가 즉시 차단한다.

## 비기능 요구

- 성능: 계획 API 응답에 예측이 추가되어도 웜 캐시 기준 5초를 넘기지 말 것.
  예측 조회가 외부 네트워크를 타지 않게 설계할 것(로컬 DB 집계).
- 정확도 고지: 예측은 참고값이며 실제와 다를 수 있음을 화면에 표기.
  기존 앱의 "참고 계산" 고지 문구 톤을 따를 것.
- 접근성: 기존 수준(WCAG AA) 유지. 혼잡도를 색으로만 표현하지 말고
  텍스트를 함께 제공할 것.
- 개인정보: 사용자의 출발지·도착지를 서버에 저장하지 말 것.
  수집하는 것은 충전소 점유 이력뿐이다.

## 하지 말 것 (스코프 가드)

- 사용자 계정·실제 로그인 인증 도입
- 충전 예약·결제 연동
- 자체 지도 렌더러 (카카오 SDK 사용)
- ML 프레임워크·모델 서빙 인프라
- 마이크로서비스 분리
- 기존 소비모델(charging.py의 온도·속도·회생 계수) 재조정.
  실측 앵커로 보정된 값이며 근거가 주석에 있다.

## 완료 기준 (측정 가능하게)

1. 예측 대기시간의 실측 대비 평균절대오차(MAE)를 리포트할 것.
2. 데이터 부족 구간에서 예측이 아니라 "데이터 부족"이 반환되는지
   테스트로 보일 것.
3. 성수기 시나리오(연휴 오전 서울→강원) 회귀 테스트를 추가할 것.
4. 기존 자체검증 3종(test_planning / test_consumption /
   test_external_stability)과 tsc --noEmit이 계속 통과할 것.
5. 쿼터 소모량을 계산해 제시할 것 — 수집기 도입 후 일일 호출 수가
   현재 대비 몇 배가 되는지, 한도 안에 드는지.

## 진행 방식

먼저 설계안을 제시하고 승인을 받은 뒤 구현할 것. 설계안에는
DB 선택 근거, 수집 대상·주기의 쿼터 역산, 콜드스타트 전략,
배포 형태 변경 여부가 반드시 포함되어야 한다.

## 5. 프롬프트에 넣은 장치와 이유

| 장치 | 이유 |
|---|---|
| "기존 자산 재사용, 재작성 금지" | 그냥 맡기면 `charging.py`를 통째로 다시 쓰려 한다. 실측 앵커로 보정된 계수가 날아간다 |
| "ML 프레임워크 도입 금지" | 초기 데이터량에선 분위수 통계가 더 정확하고 유지보수가 싸다. 서빙 인프라는 Render 무료 512MB에 들어가지도 않는다 |
| "콜드스타트 시 추측값 금지" | 근거 없는 대기시간 예측이 곧 방전 위험이다. 모르면 모른다고 해야 한다 |
| "쿼터 역산을 코드 주석에" | 수집기가 쿼터를 태워 **본 기능이 먼저 죽는 것**이 가장 흔한 실패 경로다 |
| "설계안 먼저 승인" | DB 도입과 배포 형태 변경은 되돌리기 비싸다 |
| "출발지·도착지 서버 저장 금지" | 기존 개인정보 방침([05 품질처리내역 A-5](05-품질처리내역.md)) 유지 |

## 6. 권장 진행 순서

```
1단계 (즉시)      F1 수집기만 배포 → 데이터 축적 시작
                  ※ 이 시점엔 사용자에게 보이는 변화가 없다
                  ※ 쿼터 소모량을 며칠 관측해 대상·주기를 조정

2단계 (2~4주 후)  F2 예측 + F3 계획 반영
                  ※ 데이터가 충분한 충전소부터 점진 적용
                  ※ 부족한 곳은 기존 고정 오버헤드로 폴백

3단계             F4 출발 시각 추천 (F2가 안정된 뒤)

별도 트랙         F5 지역 탐색 지도 — F1~F4와 의존성이 없어
                  언제든 독립적으로 진행 가능
```

F5는 다른 기능과 의존성이 없으므로, 데이터가 쌓이길 기다리는 동안 진행하기 좋다.
