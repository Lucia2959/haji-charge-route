## 1. 실측으로 확정된 API 사실

설계의 전제입니다. 전부 직접 호출로 확인했습니다(2026-08-04).

### 1-1. `getChargerStatus`는 상태변경 피드다

```
GET /B552584/EvCharger/getChargerStatus?pageNo=1&numOfRows=9999&period=10
```

| 항목 | 실측값 |
|---|---|
| 전국 totalCount | **13,629건 / 10분** → `numOfRows=9999` 기준 **2페이지** |
| `period` 파라미터 | **무시됨.** 10 / 60 / 1440 모두 동일한 totalCount → **10분 윈도로 고정** |
| `zcode` 필터 | 동작함. 서울(11) 1,820 · 경기(41) 2,880 · 강원(51) 949 · 충북(43) 551 |
| `numOfRows=9999` | 정상. 9,999건 반환 |
| 응답 필드 | `busiId · statId · chgerId · stat · statUpdDt · lastTsdt · lastTedt · nowTsdt` |

⚠ **`period`가 무시된다는 것은 폴링 주기의 상한이 10분으로 고정된다는 뜻입니다.**
10분을 넘겨 폴링하면 그 사이의 상태 변경을 영구히 놓칩니다.

### 1-2. 필드 의미 (실측 검증)

| 필드 | 의미 | 검증 |
|---|---|---|
| `nowTsdt` | **현재 진행 중인 세션의 시작 시각** | 채워진 행 1,942 ≈ `stat=3`(충전중) 1,934 → **충전중일 때만 채워짐**. 일치 |
| `lastTsdt` / `lastTedt` | **직전 완료 세션의 시작/종료 시각** | 9,999행 중 **9,708행(97%)** 채워짐 |
| `stat` | 기존 코드 `_STAT_LABELS`와 동일 코드계 | 2(충전가능) 7,788 · 3(충전중) 1,934 |

**이것이 설계를 바꾸는 지점입니다.** 원안은 10분마다 "지금 몇 대 쓰는 중"을 찍는
**표본 수집**이었는데, 실제로는 **세션 단위 이벤트 로그**를 얻을 수 있습니다.

- 평균 충전 점유시간을 **추정 상수(30분)로 가정할 필요가 없습니다** → 충전소별 측정값
- 점유율은 세션에서 **역산**됩니다 → 별도 점유 테이블 불필요
- 첫 폴링만으로 전국 9,700여 충전기의 **직전 세션 1건이 즉시 들어옵니다** (백필 효과)

### 1-3. 강원 시도코드는 42가 아니라 **51**

```
getChargerInfo zcode=42 → totalCount = 0      (강원특별자치도 개편 전 코드, 폐기됨)
getChargerInfo zcode=51 → totalCount = 17,767 ← 강원
getChargerInfo zcode=51&zscode=51150 → 2,477  ← 강릉
```

기존 코드는 카카오 `coord2regioncode`에서 코드를 받아 쓰므로 영향이 없지만,
수집 대상 시군구를 **하드코딩하면 안 되는 이유**입니다. 행정구역 개편으로 코드가 죽습니다.
→ `COLLECT_DISTRICTS`를 환경변수로 두고, 기동 시 각 코드의 `totalCount > 0`을 검증합니다.

### 1-4. 시도 단위 카탈로그 조회는 금지

```
getChargerInfo zcode=41 (경기) → 154,346 행   = 16 페이지
getChargerInfo zcode=11 (서울) →  75,782 행   =  8 페이지
```

한 번에 파싱하면 Render 512MB를 넘깁니다. **카탈로그는 지금처럼 시군구 단위로만 조회합니다**
(강릉 2,477행 수준). 기존 `_get_catalog`를 그대로 씁니다 — 변경 없음.

## 2. 수집 설계와 쿼터 역산

### 2-1. 전국 무필터가 시도 필터보다 싸다

| 방식 | 회당 호출 | 5분 주기 일 호출 | 커버리지 |
|---|---|---|---|
| **전국 무필터 (2페이지)** | **2** | **576** | 전국 |
| 시도 필터 11+41+51 (각 1페이지) | 3 | 864 | 3개 시도 |
| ~~시군구 20개 `getChargerInfo` 폴링~~ (원안) | 20 | 5,760 | 20개 시군구 |

전국 피드가 **호출도 적고 커버리지도 넓습니다.** 시도 필터를 쓸 이유가 없습니다.

### 2-2. 주기 5분

윈도가 10분 고정이므로 **10분이 상한**입니다. 5분으로 잡아 **2배 겹치게** 합니다.

- 크론 지연·인스턴스 슬립 복귀로 한 번 밀려도 결측이 생기지 않습니다.
- 중복분은 PK(`station_id, charger_id, started_at`)로 무시되므로 비용이 없습니다.
- 5분과 10분의 차이는 일 288 호출 — 한도의 3%. **안전 마진을 사는 값으로 쌉니다.**

### 2-3. 쿼터

```
상태 피드 : 2 페이지 × (60/5) × 24 = 576 회/일
카탈로그  : 회랑 20 시군구 × 24h TTL =  20 회/일
기존 사용 : 사용자 계획·상세          ≈ 300 회/일 (여유 있게)
──────────────────────────────────────────────
합계                                 ≈ 896 회/일
개발계정 한도                          10,000 회/일
사용률                                  약 9%
```

원안 32% → **9%**. 여유가 10배 이상이라 나중에 대상을 넓힐 여지가 큽니다.

### 2-4. 안전장치

- 수집기 **자체 일일 예산 카운터**(기본 2,000). 초과 시 그날 수집 중단 — 계획 API 몫을 지킵니다.
- `QuotaExceeded` 발생 시 즉시 그날 수집 중단 (재시도 금지 — 당일 회복 안 됨).
- 기존 `_fetch_sem`(=4)을 **그대로 공유**합니다. 전용 세마포어를 새로 만들면 전체 동시
  호출이 8이 되어 [04-운영이슈](04-운영이슈.md)의 금지 사항 위반입니다.

> ⚠ **사전 확인:** 위 계산은 개발계정 기본 10,000건 가정입니다.
> data.go.kr 마이페이지 → 활용현황에서 실제 한도를 확인해야 합니다.

## 3. DB 선택

### 3-1. SQLite가 탈락하는 이유 — 데이터 양이 아니라 디스크

**Render 무료 웹 서비스의 파일시스템은 휘발성입니다.** 재배포·재시작마다 초기화되고,
영구 디스크는 유료 플랜 기능입니다. 몇 주 모은 세션 로그가 다음 배포에서 사라지면
콜드스타트가 영원히 끝나지 않습니다. 탈락 사유는 오직 저장 매체입니다.

### 3-2. 저장 대상은 쿼터가 아니라 용량이 정한다

전국 피드는 공짜로 받지만, **전국을 다 저장하면 500MB를 못 버팁니다.**

```
세션 1행 : station_id + charger_id + started_at + ended_at + PK 인덱스 ≈ 80 B

[전국 저장 시]   신규 세션 추정 10만 건/일 → 8 MB/일 → 240 MB/월   ❌ 4개월이면 한계
[회랑만 저장]    20 시군구 급속·개방 약 300 개소 × 4 기 × 7 세션/일
                ≈ 8,400 건/일 → 0.7 MB/일 → 21 MB/월   ✅ 12개월 250MB
```

**따라서 회랑 제한은 유지하되, 근거가 바뀝니다** — 쿼터가 아니라 저장 용량 때문입니다.
용량 여유가 확인되면 코드 수정 없이(`COLLECT_DISTRICTS` 확장) 넓힐 수 있습니다.

회랑(영동 · 서울양양 축):

| 축 | 시군구 |
|---|---|
| 영동 | 서울 서초·강남, 경기 성남·용인·광주·이천·여주, 강원 원주·횡성·평창·강릉 |
| 서울양양 | 경기 하남·남양주·가평, 강원 춘천·홍천·인제·양양·속초 |

### 3-3. 선택

| 후보 | 판정 |
|---|---|
| SQLite (파일) | ❌ Render 무료 디스크 휘발 |
| Render 무료 Postgres | ⚠ 무료 인스턴스 **만료 정책** 존재 → 만료 시 소실. 착수 전 현행 정책 확인 필요 |
| **Neon 무료** | ✅ 0.5GB, 만료 없음. 유휴 자동 절전(재개 1초 미만) — 5분마다 쓰므로 진입 안 함 |
| **Supabase 무료** | ✅ 0.5GB, 만료 없음. 7일 무활동 시 일시정지 — 해당 없음 |

**Neon 또는 Supabase.** 동등하므로 이미 쓰는 쪽을 고르면 됩니다.

### 3-4. 접근 계층 — ORM 없음

```
asyncpg          asyncio 네이티브, FastAPI와 동일 루프
app/db.py        커넥션 풀 1개(min 1 / max 2), lifespan에 부착
app/schema.sql   CREATE TABLE IF NOT EXISTS, 기동 시 1회 실행
```

SQLAlchemy / Alembic **도입하지 않습니다.** 테이블 2개·쿼리 4개 규모에 마이그레이션
프레임워크는 유지보수 부담만 늘립니다. 풀 크기 2인 이유는 무료 Postgres의 동시 접속
한도가 낮고 단일 워커라 그 이상이 필요 없기 때문입니다.

## 4. 배포 형태 — 바뀌는 것과 바뀌지 않는 것

### 4-1. 수집기는 별도 프로세스가 아니다

프롬프트는 "분리된 워커"를 요구했지만 **Render 무료 플랜에 Background Worker가 없습니다**(유료 전용).

| 안 | 평가 |
|---|---|
| 앱 내부 `asyncio` 백그라운드 태스크 | ❌ 무료 인스턴스는 유휴 15분 후 슬립 → 타이머가 죽고 그 사이 결측 |
| **`POST /internal/collect` + 외부 크론** | ✅ 채택 |

```
cron-job.org ──5분마다──▶ POST /internal/collect   (X-Collect-Key)
                                │
                                ├─ getChargerStatus 전국 2페이지  (_fetch_sem 공유)
                                ├─ 대상 statId 필터 → session UPSERT
                                └─ 200 {"rows": 13629, "sessions_new": 91}
```

- **기존 keep-alive 크론(`/health` 10분)을 이것으로 대체**합니다. 이 호출 자체가
  keep-alive라 크론이 하나로 줄고, [TODO.md](../TODO.md)의 `/heath` 오타 건도 같이 정리됩니다.
- 토큰은 `API_TOKEN`과 **분리**(`COLLECT_TOKEN`)합니다. `API_TOKEN`은 프런트 번들에
  노출되므로 그걸로 수집을 트리거할 수 있으면 누구나 쿼터를 태울 수 있습니다.
- `/internal/*`은 rate limit 1분 2회, 사용자 경로(`/api/*`)와 분리합니다.

**"사용자 요청 경로에 넣지 말 것"은 지켜집니다.** 다만 같은 프로세스·같은 이벤트 루프를 씁니다.
영향은 XML 13,629행 파싱 CPU **약 0.26초**(실측 19μs/행 기준)가 5분에 한 번 들어가는 정도입니다.

### 4-2. 단일 인스턴스·단일 워커 제약은 **유지**

DB가 생기면 풀리는지에 대한 답은 **아니오**입니다.

| 상태 | 위치 | DB로 옮기나 |
|---|---|---|
| `_catalog_cache` (24h) | 메모리 | ❌ 외부 API 절약이 목적, DB로 옮길 이유 없음 |
| `_status_cache` (20s) | 메모리 | ❌ 20초 캐시를 DB에 넣으면 왕복이 더 비쌈 |
| `_station_region` | 메모리 | ❌ |
| rate limit 버킷 | 메모리 | ❌ Redis가 있어야 공유 가능 |
| 충전 세션 로그 | **DB (신규)** | ✅ |

워커를 늘리면 여전히 rate limit이 워커 수만큼 곱해지고 캐시가 쪼개집니다.
**`--workers 1` 유지, 인스턴스 1개 유지.** [render.yaml](../render.yaml) 주석 그대로 유효.

DB가 실제로 푸는 것은 하나뿐입니다: **재배포해도 세션 로그가 살아남는다.**

## 5. 스키마

```sql
-- 완료된 충전 세션. lastTsdt/lastTedt 쌍에서 적재.
CREATE TABLE IF NOT EXISTS session (
  station_id text        NOT NULL,
  charger_id text        NOT NULL,
  started_at timestamptz NOT NULL,
  ended_at   timestamptz NOT NULL,
  PRIMARY KEY (station_id, charger_id, started_at)
);
CREATE INDEX IF NOT EXISTS session_station_start_idx
  ON session (station_id, started_at);

-- 예측 조회용 집계. 매일 새벽 1회 갱신.
CREATE TABLE IF NOT EXISTS occupancy_stat (
  station_id  text     NOT NULL,
  daytype     smallint NOT NULL,   -- 0=평일 1=주말 2=연휴
  hour        smallint NOT NULL,   -- 0..23
  n_days      smallint NOT NULL,   -- 관측된 날 수 (콜드스타트 판정)
  occ_mean    real     NOT NULL,   -- 평균 점유율
  p_full      real     NOT NULL,   -- 전 충전기 사용중이던 시간 비율
  svc_min_med real     NOT NULL,   -- 세션 길이 중앙값(분) — 측정값
  updated_at  timestamptz NOT NULL,
  PRIMARY KEY (station_id, daytype, hour)
);
```

- **점유 테이블이 없습니다.** 점유율은 세션 구간에서 역산합니다
  (시각 t의 사용중 대수 = t를 포함하는 세션 수).
- 요일유형·시간대는 `session`에 저장하지 않습니다 — `started_at`에서 유도되고,
  연휴 판정은 달력이 바뀔 수 있어 **집계 시점에** 적용합니다.
- 연휴 달력은 코드 상수(`_HOLIDAYS: set[date]`). 공공 특일정보 API를 하나 더 붙이는 것보다
  연 1회 상수 갱신이 쌉니다.
- `ON CONFLICT DO NOTHING` — 5분 폴링의 2배 중복이 그대로 무시됩니다.

### F1. 수집기 — `app/services/collector.py`

```python

    """getChargerStatus 전국 피드 1회 → 대상 충전소 세션 UPSERT."""
```

핵심 로직은 이게 전부입니다:

```python
for row in rows:
    if row["statId"] not in TARGET_IDS:      # 회랑 급속·개방 충전소
        continue
    ts, te = row.get("lastTsdt"), row.get("lastTedt")
    if ts and te:

executemany("INSERT ... ON CONFLICT DO NOTHING", pending)
```

- `TARGET_IDS`는 회랑 20 시군구 카탈로그에서 만듭니다: 급속(`chgerType != "02"`)
  **AND** `_access_class` 결과가 `open`/`open_fee`. 입주민·관계자 전용은 계획 후보가
  아니므로 이력도 모으지 않습니다. 카탈로그 TTL(24h)에 맞춰 하루 1회 갱신.
- `getChargerStatus`에는 위치·타입이 없으므로 **카탈로그와 `statId`로 조인**합니다.
  기존 `_get_catalog` / `_station_region`을 그대로 씁니다.
- 세션 길이가 비정상인 행은 버립니다 (`ended_at <= started_at`, 또는 12시간 초과 —
  완속 야간 방치·기기 오류).

### F2. 예측 — `app/services/congestion.py`

**큐잉 모형을 가정하지 않습니다.** 세션 로그에서 점유 시계열을 재구성해 경험분포를 씁니다.

일 1회 집계 (SQL 한 방):

```
셀 = (station_id, daytype, hour)
occ_mean    = 그 셀의 분(minute) 단위 사용중 대수 평균 / 충전기 수
p_full      = 사용중 대수 == 충전기 수 였던 분의 비율
svc_min_med = 그 셀에서 시작한 세션 길이의 중앙값
n_days      = 그 셀을 관측한 서로 다른 날짜 수
```

조회·예측 (계획 1건당 쿼리 1회, 외부 네트워크 없음):

```python
async def load_stats(station_ids, daytype, hour) -> dict[str, Row]:  # IN 절 배치 1쿼리
def predict_wait(row) -> Prediction:                                  # 순수 함수
```

**대기시간 추정** — 두 입력이 모두 측정값입니다:

```
기대 대기(분) = p_full × (svc_min_med / 2)
                 └ 측정      └ 측정 (원안의 가정 상수 30분을 대체)
표시 구간     = [기대대기 × 0.7, 기대대기 × 1.5], 5분 단위 반올림
```

`svc_min_med / 2`는 만차 상태로 도착했을 때의 **평균 잔여 서비스 시간** 근사입니다.
충전 세션 길이가 결정론적에 가까워(급속 80% ≈ 일정) 지수분포를 가정하는 Erlang-C보다
경험값이 낫습니다.

혼잡 등급 — **색만으로 표현하지 않고 텍스트 병기** (WCAG 유지):

| 등급 | 조건 | 표시 |
|---|---|---|
| 여유 | `occ_mean < 0.5` | "여유" |
| 보통 | `0.5 ≤ occ_mean < 0.8` | "보통" |
| 혼잡 | `occ_mean ≥ 0.8` 또는 `p_full ≥ 0.3` | "혼잡 예상" |
| 데이터 부족 | `n_days < 8` | "데이터 부족 — 대기시간 미반영" |

### F3. DP 연동 — `charging.py` 순수성 유지

콜백 **하나만** 추가합니다. DB·네트워크 의존을 들이지 않습니다.

```python
def plan_charging_dp(..., wait_min_fn: Callable[[str, float], float] | None = None):
    ...
    ct = (
        _charge_minutes(a_soc, d_soc, power_i, cap)
        + _STOP_OVERHEAD_MIN
        + (wait_min_fn(st_i.id, base) if wait_min_fn else 0.0)  # base = 이 노드까지 경과분
        + 2 * off_i / v * 60.0
        + exit_penalty
    )
```

**상태 차원을 늘리지 않아도 되는 이유:** `dp[i][ai]`가 이미 "그 노드에 그 SoC로 도착하는
최소 경과시간(분)"입니다. 도착 시각 = `출발시각 + base` → 시각을 상태로 따로 들 필요가
없습니다. 격자 크기가 그대로라 계산량도 그대로입니다.

> `# ponytail:` 근사입니다. 대기가 시간에 따라 변하므로 "더 늦게 도착하는 경로가 총합은
> 더 짧은" 경우를 놓칠 수 있습니다. 실측에서 문제가 되면 그때 시간 차원을 추가합니다.
> 지금 넣으면 상태 수가 (시간 버킷 수)배가 됩니다.

`wait_min_fn`은 `load_stats()` 결과를 담은 클로저라 **DP 실행 중 DB를 치지 않습니다.**
`n_days < 8`인 충전소는 `0.0`을 반환 → 자동으로 기존 고정 오버헤드로 폴백됩니다.

**대안 제시:** 계획 확정 후, 혼잡 등급인 충전소마다 앞/뒤 후보로 바꾼 DP를 1회씩 더
실행해 총 시간을 비교합니다. 개선폭 10분 이상이면 노출. DP는 웜 0.4초라 예산 안입니다.

## 7. 콜드스타트 전략

**임계값 `n_days ≥ 8`** (셀 = 충전소 × 요일유형 × 시간대).

세션 로그는 이벤트 기록이라 첫 폴링부터 **직전 세션 1건이 즉시 백필**되지만,
시간대별 점유 통계를 세우려면 그 셀을 실제로 관측한 날 수가 쌓여야 합니다.

| 요일유형 | 주당 관측일 | `n_days ≥ 8` 도달 |
|---|---|---|
| 평일 (주 5일) | 5 | **약 2주** |
| 주말 (주 2일) | 2 | **약 4주** |
| 연휴 | 연간 며칠 | 수개월~불가 |

- **연휴는 별도 학습하지 않습니다.** `n_days ≥ 8`에 닿기 전까지 **주말 통계로 대체**하고
  응답에 `daytype_fallback: "weekend"`를 명시합니다. 주말 통계를 연휴에 쓰면 과소추정이므로
  화면에 **"연휴에는 더 붐빌 수 있음"**을 병기합니다.
- `n_days < 8`이면 예측값을 만들지 않고 `{"status": "insufficient_data", "n_days": 5}`를
  반환합니다. **추측값을 내지 않습니다.** 이 경로를 테스트로 고정합니다(완료기준 2).
- 따라서 **F1을 먼저 배포하고 2~4주 뒤 F2·F3를 켭니다.** 순서를 바꾸면 전 구간이
  "데이터 부족"만 반환합니다.

## 9. 완료 기준 (수정본)

| # | 기준 | 검증 방법 |
|---|---|---|
| 1 | **점유율 예측 MAE** + 만차확률 Brier score + **세션길이 MAE** | 8주 학습 / 2주 검증 시간분할 백테스트 (~~대기시간 MAE~~ — 9-1 참조) |
| 2 | 데이터 부족 시 `insufficient_data` 반환 | `test_congestion.py` — `n_days=7` → 부족, `8` → 예측 |
| 3 | 성수기 시나리오 회귀 테스트 | 연휴 오전 서울→강릉, 대기 반영/미반영 계획 비교 |
| 4 | 기존 자체검증 3종 + `tsc --noEmit` 통과 | 변경 없음 |
| 5 | 쿼터 소모량 제시 | 2-3장. 현재 대비 **약 3배**, 한도의 **9%** |

### 9-1. 완료기준 1을 바꿔야 하는 이유

공공 API는 **대기열 길이도, 대기 시간도 제공하지 않습니다.** 줄 서 있는 차는 어떤 필드에도
나타나지 않습니다. 따라서 "실측 대기시간"이라는 정답 레이블이 없고 그에 대한 MAE는
정의될 수 없습니다.

다만 원안보다 상황은 나아졌습니다 — 추정식의 두 입력(`p_full`, `svc_min_med`)이
**모두 측정 가능하고 각각 백테스트로 검증됩니다.** 대기시간은 그 둘에서 유도한
파생 추정치이므로, 화면에도 "대기 25분"이 아니라 **"혼잡 예상 · 20~30분"** 구간으로
표기하고 참고값 고지를 붙입니다.
