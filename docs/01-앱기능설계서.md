# 앱 기능설계서 — Haji Charge Route

> BYD 돌핀 스탠다드 전기차 **충전 경로 안내 웹앱**
> 인수인계 기준일: 2026-08-01 / 대상 브랜치: `main`

---

## 1. 개요

### 1.1 목적

출발지·도착지·현재 충전량을 입력하면, **경로상 어디서 몇 %까지 충전해야 목적지까지
안전하게 도달하는지**를 계산해 안내한다. 단순 "충전소 찾기"가 아니라 **주행 가능
거리(유효거리) 예측 + 충전 계획 최적화**가 핵심이다.

### 1.2 적용 범위

| 항목 | 내용 |
|---|---|
| 대상 차량 | BYD 돌핀 스탠다드 (49.92kWh LFP 블레이드) **1종 고정** |
| 대상 지역 | 대한민국 (공공데이터포털 충전소 API 커버리지) |
| 사용자 | 단일 개인 사용자 (계정·인증 없음) |
| 디바이스 | 모바일 웹 (iPhone Safari 홈 화면 추가 = PWA standalone) |
| 성격 | **비공식 개인 테스트 앱**. 상업 서비스 아님 (Vercel Hobby 비상업 조건) |

### 1.3 비적용 범위 (설계상 의도적으로 하지 않는 것)

- 사용자 계정·로그인 인증 (로그인 화면은 진입 연출일 뿐 인증 없음)
- 실제 내비게이션(턴바이턴 안내), 음성 안내
- 충전 예약·결제·회원 연동
- 다중 차량·차종 선택
- 오프라인 동작 (서비스워커 없음)

## 4. 핵심 알고리즘 설계

### 4.1 소비전력 예측 (`consumption_wh_per_km`)

기준소비(60km/h·온화) 위에 **네 성분을 물리적으로 분리**해 얹는다.

```
소비(Wh/km) = 견인 + 보조부하 + 온도-공조 + 온도-배터리

1) 견인      = traction_ref / speed_factor(v)   (공기저항 ∝ v², 일반도로는 ×0.93 회생)
2) 보조부하  = 0.6kW × 1000 / v                 (시간기반 → 저속에서 급증)
3) 온도-공조 = 0.5 × penalty × 60 / v           (HVAC, 시간기반)
4) 온도-배터리 = 0.5 × penalty                   (저온저항·회생저하, 속도 무관)

penalty = base × (1/temp_factor − 1)
```

**왜 3)/4)를 나누는가:** 온도 페널티를 100% 시간기반으로 두면 "겨울 고속도로 소비 ≈
겨울 일반도로 소비"로 수렴해 공기저항 페널티가 사라지고, **고속 유효거리를
과대평가 = 방전 위험**이 된다. 거리기반 성분을 분리하면 고속 주행의 온도 페널티가
유지된다. `_TEMP_HVAC_FRAC`를 낮출수록 보수적(안전)해진다.

기준속도(60km/h)에서는 3)+4)의 합이 penalty 전체와 같아, **온도 앵커 보정이 보존**된다.

### 4.2 온도 보정계수 (`temp_factor`)

Geotab(500만 트립)·AAA 실측 앵커의 선형보간.

| 기온 | 계수 | 근거 |
|---|---|---|
| -20°C | 0.50 | Geotab 외삽 |
| -15°C | 0.54 | Geotab |
| -7°C | 0.61 | AAA (-39%) |
| 0°C | 0.80 | |
| 10~24°C | 1.00 | 냉난방 거의 불필요 |
| 31°C | 0.94 | Geotab (에어컨 상시 ~5%) |
| 35°C | 0.85 | AAA(-17%)와 Geotab 사이, 보수 쪽 |
| 40°C | 0.78 | |

> **환경부 저온 인증(0.80 @-7°C)보다 보수적으로 잡은 이유:** 인증은 예열된 차량으로
> 짧은 표준 사이클을 도는 시험이라 장시간 히터 주행보다 손실이 작게 나온다.
> 충전계획은 거리를 과대평가하면 방전 위험이므로 실측 기준을 유지한다.

### 4.3 유효거리 산출 (`effective_range_from_segments`)

```
segments: [(거리km, 실제속도km/h, 도로등급), ...]      ← 카카오 도로별
도로등급 = "highway"(고속도로) | "expressway"(자동차전용) | "local"
총 소비 Wh = Σ 거리 × consumption_wh_per_km(속도, 온도, 도로유형)
유효거리   = 배터리용량(Wh) / (총소비 / 총거리)
```

총평균속도가 아니라 **구간별 실제 교통속도**로 적산하므로, 정체 구간이 많은 경로일수록
유효거리가 정확히 줄어든다.

### 4.3.1 사용자 순항속도 (`apply_cruise_speed`)

`cruise_speed_kmh`(선택 입력)는 **고속도로·자동차전용 구간에만** 반영된다.

```
구간속도 = min( clamp(희망속도, 법정최저, 법정최고), 실시간 교통속도 )
```

| 도로등급 | 법정 범위(대표값) | 근거 |
|---|---|---|
| `highway` 고속도로 | 50 ~ 110 km/h | 최고는 노선별 100·110·120 → 높은 쪽으로 대표(소비 과대 = 안전) |
| `expressway` 자동차전용 | 30 ~ 90 km/h | 최고 80~90 |
| `local` 일반도로 | **미적용** | 제한속도 편차가 30~80으로 너무 커, 실시간 교통속도가 더 나은 추정치 |

두 단계 각각의 이유:

- **clamp** — 120을 원해도 그 도로에서 낼 수 없는 속도는 계산에 넣지 않는다. 반대로
  20을 넣어도 법정 최저 미만으로는 내려가지 않는다.
- **min** — **정체를 지우지 않기 위해서다.** 희망속도로 덮어쓰면 상습정체 구간이
  100km/h로 계산되어 소비가 과소평가되고, 그게 곧 방전 위험이다. `test_consumption.py`가
  이 불변식을 고정한다.

따라서 **입력값보다 낮은 속도로 계산되는 것이 정상**이다. 실측(서울→강릉, 2026-08-04):

| 입력 | 실제 계산속도 | 유효거리 | 비고 |
|---|---|---|---|
| 미입력 | 94.1 km/h | 241.3 km | 실시간 교통속도 그대로 |
| 80 | 78.6 km/h | 263.5 km | 느리게 달려 +22km |
| 100 | 93.6 km/h | 242.0 km | 교통이 94라 거의 변화 없음 |
| 120 | 94.0 km/h | 241.4 km | 110으로 clamp 후 교통이 상한 |

> `speed_factor` 응답 필드는 **단일 속도의 계수가 아니다.** 구간별 소비를 적산한 뒤
> `유효거리 ÷ (정격 × 온도계수)`로 역산한 **등가값**이라 회생·보조부하·공조가 모두
> 섞여 있다. 같은 경로라도 시간대(교통)에 따라 달라진다.

### 4.4 충전 계획 DP (`plan_charging_dp`)

**목적함수:** 총 소요시간(주행 + 충전 + 오버헤드 + 진출입 패널티) 최소화

| 요소 | 정의 |
|---|---|
| 상태 | `dp[node][soc]` = 해당 노드에 해당 SoC로 도착하는 최소 시간(분) |
| 노드 | 출발지(0) → 후보 충전소(경로순) → 목적지 |
| 전이 | 전 구간 쌍(all-pairs). 노드 i에서 (선택적 충전 후) 도달 가능한 j로 직행 |
| SoC 격자 | 0~100%, 5% 단위 (`soc_step`) |
| 제약 | 출발 SoC ≥ reserve, 목적지 도착 SoC ≥ `_DEST_MIN_SOC`(15%) |
| 충전시간 | `Σ (1%당 에너지 / min(충전기kW, 차량커브kW) / 0.9)` |

**충전 커브(`_CHARGE_CURVE`)** — SoC별 차량 수용 출력(kW):

```
0%:70 → 30%:68 → 40%:64 → 50%:60 → 60%:54 → 70%:46 → 80%:35 → 90%:20 → 100%:10
```
실측 앵커 검증: 30→80% **31.0분** (BYD 공식 30분), 10→80% **40.7분** (EVKX 38.5분).
공식값보다 살짝 보수적으로 잡아 계획 시간이 부족해지지 않게 했다.

**후보 축소(`_select_candidates`):** 경로를 20km 구간으로 나눠 구간당 상위 2개.
정렬 기준은 `휴게소 우선 → 고출력 → 근접`. IC 진출 충전소는 폴백으로만 남긴다.

**SoC 격자를 0부터 만드는 이유:** reserve(10%)부터 시작하면 "현충전량 5%" 같은
안전마진 미만 상태가 10%로 올려붙어 실제보다 낙관적인 계획이 나온다. 0까지 두면
출발 제약이 자연히 infeasible을 만들어 선충전 안내로 이어진다.

### 4.5 greedy 폴백 (`recommend_charging_stops`)

DP가 `feasible=False`를 반환하면 **도달가능성 우선** greedy로 전환한다.
ABRP·Tesla 등 EV 경로 플래너의 표준 접근: 현재 도달 범위 안에서 **가장 멀리 갈 수
있는** 충전소를 선택하고 반복. 각 단계마다 도달 가능성을 보장한다.

### 4.6 충전소 접근성 분류 (`_access_class`)

`limitYn` / `limitDetail` 텍스트로 5분류. **판정 순서가 중요하다.**

| 분류 | 키워드 예 | 외부인 |
|---|---|---|
| `open` | `limitYn != "Y"` | ✅ |
| `open_fee` | 방문객, 고객, 이용객, 투숙 | ✅ (주차비 발생 가능) |
| `residents` | 입주민, 거주자, 입주사, 세대, 아파트 | ❌ |
| `staff` | 임직원, 관계자, 비개방, 출입불가 | ❌ |
| `fleet` | 전기버스, 화물차, 택시, 카셰어링, 관용, 군부대 | ❌ |

> **방문객 키워드를 입주·관계자보다 먼저 검사한다.** "입주사 방문객"처럼 방문객은
> 쓸 수 있는데 과차단되던 문제 때문. `fleet`을 사용불가로 넣은 이유는, 전기버스
> 전용 충전소를 추천하면 도착 후 충전 불가 = 방전 위험이기 때문이다.

접근성 판정은 **계획 수립 전에** 적용한다 (`stations_near_path`에서
`public_access=False`를 아예 제외). 계획을 세운 뒤 "사용불가" 표시만 하면 정작
계획의 중심이 못 쓰는 충전소가 되어 경로가 흔들린다.

### 4.7 선충전 권장 (`origin_precharge_advice`)

두 가지 상황에서 발생한다.

| 상황 | 하한 | 필요거리 |
|---|---|---|
| 1차 충전소까지 (`is_destination=False`) | `reserve_pct` (10%) | `max(target×1.15, target+8km)` |
| 목적지 직행 (`is_destination=True`) | `max(reserve, 15%)` | `target×1.15` |

**`max`를 쓰고 합산하지 않는 이유:** 두 위험(정체로 추가소모 / 현장 사용불가)은
동시 발생을 가정하지 않는다. 합산하면 과다 권장이 된다.

## 6. 업무 규칙 (Business Rules)

| ID | 규칙 |
|---|---|
| **BR-01** | 안전마진 = `max(10%, 25km 환산%)`. 겨울·정체로 유효거리가 줄면 자동 상향 |
| **BR-02** | 목적지 도착 시에도 최소 15% 잔량을 남긴다 (목적지 충전소 점유·고장 대비) |
| **BR-03** | 입주민·관계자·특정차량 전용 충전소는 **계획 후보에서 제외** |
| **BR-04** | 출발지·목적지 ±2km 내 충전소는 "정지 지점"으로 부적절 → DP 후보 제외 |
| **BR-05** | 같은 충전소를 두 번 배정하지 않는다 (greedy `used` 집합) |
| **BR-06** | `MOCK_ENABLED=false`(운영)에서는 **mock 폴백 금지**. 실제로 없는 충전소를 추천하거나 직선 경로를 실제 경로처럼 쓰는 것을 막는다 |
| **BR-07** | 지오코딩 실패 시 서울로 폴백하지 않고 400 오류 반환 (운영 모드) |
| **BR-08** | 충전 계획 결과·검색조건은 sessionStorage에 **3시간 TTL**로만 보관 |
| **BR-09** | 즐겨찾기 주소는 서버·번들 어디에도 두지 않고 기기 localStorage에만 저장 |

## 7. 오류 처리 정책

| 상황 | HTTP | 화면 메시지 | 근거 |
|---|---|---|---|
| 주소 검색 실패 | 400 | "출발지 또는 도착지를 찾을 수 없습니다" | `kakao.LocationNotFound` |
| 경로 조회 실패 | 502 | "실제 도로 경로를 조회하지 못했습니다" | `kakao.RouteUnavailable` |
| 외부 API **쿼터 소진** | **402** | "사용량이 초과하였습니다" | `QuotaExceeded` — 그날 회복 안 됨 |
| 외부 API **일시 제한** | **429** | "요청이 몰리고 있습니다. 잠시 후…" | `RateLimited` — 몇 분 뒤 정상 |
| 앱 자체 요청 제한 | 429 | "요청이 너무 많습니다. N초 후…" | `ratelimit.py` |
| 토큰 불일치 | 401 | "접근 권한이 없습니다" | `require_token` 미들웨어 |
| 충전소 없음 | 404 | "충전소를 찾을 수 없습니다" | |

> **402와 429를 반드시 구분한다.** 429를 "사용량 초과"로 표시하면 사용자가 "오늘은
> 못 쓴다"고 오해하지만 실제로는 몇 분 뒤 정상 동작한다. 공공데이터포털은 쿼터
> 소진을 두 형태로 보내므로(HTTP 200 + XML `returnReasonCode 22`, HTTP 429 +
> 평문 `quota exceeded`) **본문까지 확인**해 판정한다(`_is_quota_body`).
